# Calendarium

Browser app (Vite + React + TypeScript) that generates a calendar to print on paper.

## Commands

- `npm run dev` / `npm run build` / `npm test` / `npm run test:e2e` (Playwright) / `npm run lint` (oxlint) / `npm run format` (`format:check` to verify only) / `npm run typecheck`
- Single test file: `npx vitest run src/core/calendar.test.ts`; single test by name: `npx vitest run -t "leap year"`
- Unit tests are plain `src/**/*.test.ts` files, DOM-free, covering `core/`, `layouts/`, `workspace/` and `preferences/`. A layout's own rules are tested in its folder (its options in `options.test.ts` through `parseOptions`, its migration steps in `migrations.test.ts`, what its pages hold in `pages.test.ts`), what every layout's spec must do in `layouts/index.test.ts` (run for each id in `LAYOUT_IDS`), and the host's tests in `workspace/` and `ui/` check only the mechanics, through any layout. Component tests are `src/**/*.test.tsx` (Vitest `component` project: jsdom + Testing Library, setup in `src/test/setupDom.ts`); they check structure only (page counts, which form sections show, the import flow), never appearance. What a layout draws and which sections its form shows are tested next to its component and form in `layouts/<layout-id>/ui/` (`formSectionTitles` in `src/test/formSections.ts` renders a form alone). Run one project with `npx vitest run --project unit` (or `component`).
- CI (`.github/workflows/build-master.yml`, on pushes to `master` and on pull requests, a pull request's new push cancelling its previous run; Chromium cached by Playwright version; a failed e2e test's trace uploaded as the `playwright-results` artifact) runs `format:check`, `lint`, `typecheck`, `test`, `build`, `test:e2e` and the visual comparison, in that order; run the same before considering a change done.
- Dependabot (`.github/dependabot.yml`) opens weekly pull requests for the npm packages and the workflows' actions; what to check before merging one, and the notes on each major upgrade, are in `doc/upgrading-dependencies.md`.
- `e2e/print.spec.ts` (Playwright, Chromium) builds the app, creates a project of each layout through the New project dialog, prints it to PDF and checks the page count and paper size, and that no page's content is clipped in print media; `e2e/projects.spec.ts` saves a project to a file and opens it back. First run needs `npx playwright install chromium`. The e2e helpers (`showLayout`, `openSection`, `openProjectFile`, `pdfPageSizes`, `clippedPages`) are in `e2e/helpers.ts`.
- `e2e/visual.spec.ts` shows which printed pages a change alters, comparing two builds rather than committed images: `npm run test:visual [base]` (`scripts/visual-diff.sh`; `base` is `HEAD` by default, so it checks the uncommitted changes; `master` or `HEAD~1` as well) builds the base commit in a temporary git worktree and the working tree, screenshots each case's pages (print media, each case a project file of partial options, opened by `openProjectFile`) on the base's build, then compares the working tree's with them, exactly (`threshold: 0`, a 0.01 % pixel allowance, in `playwright.config.ts`), keeping each changed page's expected, actual and diff images in `test-results/`. Both builds are drawn on the same machine, so fonts don't matter and nothing is stored; `npm run test:e2e` skips these tests. Before considering a change done, run it: a change meant to alter how pages look must alter only the pages it means to (look at the diffs), any other must alter none. CI runs it on every push to `master` (against the commit before) and pull request (against its base) without failing the build, uploading the images as the `playwright-results` artifact. A layout's new option that changes its look deserves a case there. Chromium snaps border widths to whole CSS pixels, so thin rules that differ by less than a pixel print the same and don't show.

## Architecture

Five folders, one per bounded context, from the bottom up: `core` ← `layouts` ← `workspace` ← `preferences` ← `ui`. Each imports only the folders below it, and only `ui/` uses React (a layout's UI, in `layouts/<layout-id>/ui/`, is `ui/`). Each layout is one unit, like a plugin of the host (everything outside the layouts' folders): its files import only its own files and the host's, never another layout's, and the host knows a layout only through its entry points, its domain `layouts/<layout-id>/index.ts` and its UI's `layouts/<layout-id>/ui/index.ts`, imported by the registries alone (`layouts/index.ts`, `ui/layouts/registry.ts`). `src/layers.test.ts` fails on any import that breaks these rules, and on a layout folder not named after an id in `LAYOUT_IDS`. It lists the files with `import.meta.glob`, so `vite.config.ts` keeps Vitest from caching such a module (`freshGlobs`), which would otherwise miss files added since.

- `src/core/` — the generic subdomains: calendar, languages and paper, knowing nothing of layouts or settings. `buildMonth` always returns 6 weeks so every month has the same height. A date is a `PlainDate` (`{ year, month, day, weekday, key }`, `key` = `YYYY-MM-DD`, the React key, `weekday` a `Weekday`, 0 = Sunday … 6 as in `Date.getDay()`; a `CalendarDay` extends it, as does a `WeekDay`, seven of which make a `Week`), never a `Date`: `plainDate` builds one, a weekday's column from the week start is `weekdayColumn`, and `utcDate` (UTC midnight, `setUTCFullYear`, so no DST and years below 100 as written) is the only place a `Date` is built, for `Intl` formatting (`dateFormatter` formats in UTC). What the app reads from where it runs, today's year and the browser's language, is an `Environment` (`environment.ts`), read only by `currentEnvironment` (the other `Date`) and passed down: `commonDefaults(env)`, each spec's `defaults(env)`, `defaultLayoutOptions`, `hasDefaultOptions` and `parseOptions` take it, the current one when not given, so tests pass a fixed one; `src/layers.test.ts` fails on a `new Date(` or `navigator` read anywhere else outside tests. `locale.ts` lists the supported `LOCALES` and derives month/weekday names from `Intl.DateTimeFormat` (through the cached `dateFormatter`) and the default week start from `Intl.Locale` week data. `events.ts` reads the event list (`CommonOptions.events`, its lines kept as typed, one `YYYY-MM-DD Name` each, year `0000` for every year; the textarea edits them as one text, `eventLines` splitting it back) into `CalendarEvent`s (`parseEvents`) and names a date's events (`eventNames`); `calendarModel` parses it once, and the month, week and day plans give each day of their month or year its `events`, and the year plan gives each month the `eventDays` its `MiniMonth` circles. Any other text printed on a page comes from the layout's own messages table (`layouts/<layout-id>/messages.ts`, like `DAY_PAGE_MESSAGES`), never a literal in a component, so a calendar is printed in one language; the app's own UI stays English. Each layout keeps its own table, even for text another layout prints too (the week and day layouts both have `week`), so layouts stay independent of one another. A new locale is one entry in `LOCALES`, its messages in each layout's table and its label in `CalendarSection` (compile-enforced). The Gregorian range (`MIN_YEAR`, `isYear`) is in `calendar.ts`; the page setup (`PageSetup`, `Margins`, their `PAGE_VALIDATORS`) in `paper.ts`; the generic checks (`Validators`, `oneOf`, …) and `copyValid`, which applies a `Validators` table to untrusted data field by field, in `validation.ts`.
- `src/layouts/` — the core domain: what each layout is and prints. `index.ts` lists the layouts once, in `LAYOUTS` (the picker's order), each the `defineLayout(id, spec)` its folder's `index.ts` exports, and derives the rest from it: `LayoutId`, `LAYOUT_IDS`, each layout's options (`LayoutOptions`: `YearlyOptions`, `MonthlyOptions`, `WeeklyOptions`, `DailyOptions`, each extending `CommonOptions` from `common.ts`, which `defineLayout` requires) and the specs. The id is stored in settings and files, so it never changes once released, except in a major release, whose migration steps map the old id to the new one (`LEGACY_LAYOUT_IDS` in `workspace/legacy.ts`, as 6.0.0 maps `year-per-page` to `yearly`). Each layout's knowledge of its options is one `LayoutSpec` in `layouts/<layout-id>/options.ts`, next to its options type: `defaults`, `validators` (extending `COMMON_VALIDATORS`), `normalize` and `migrations` (its own steps between format versions, in `layouts/<layout-id>/migrations.ts`, `{}` when it has none); `parseOptions(spec, data)` (`LayoutSpec.ts`) reads untrusted options by them. `index.ts` collects the specs in `LAYOUT_SPECS` and exposes `layoutSpec(id)`, `defaultLayoutOptions`, `normalizeLayout`, `migrateLayoutOptions` and `mapLayouts`; the first of the `LAYOUT_IDS` is the one the New project dialog preselects. Everything only one layout uses lives in its folders; what several share stays in the host (`common.ts`, `monthGrid.ts`, `schedule.ts`, `heading.ts`, `migrations.ts`). Rules a layout's pages follow sit next to its options, like `weekly/cells.ts` (`weekCells`, `splitWeekCells`).
- `src/workspace/` — the saved projects, apart from the viewer preferences. A `Project` (`Project.ts`) is one calendar being made: its `id` (a `ProjectId`, a lowercase v4 UUID, `isProjectId`; `newProjectId` builds one from `crypto.getRandomValues`, since `crypto.randomUUID` needs a secure context and the release zip may be served over plain HTTP), its `name` (kept as typed, `''` for none, trimmed only to show it or name a file, and never printed: the printed title is `header.title`), its `layout`, chosen when it is created and never changed afterwards, and that layout's `options`; `Project<ProjectId | null>` is one read from a file that has no id yet. The `Workspace` (`Workspace.ts`; `defaultWorkspace` is empty) holds every project kept in this browser, by id, and the `open` one, `null` when there is none: `openProject(workspace)` gives it, and `projectList` orders the projects as the Open project dialog lists them (by trimmed name, the unnamed ones last, then by id). `Workspace` is the aggregate root: it changes only through the commands of the pure `workspaceReducer` (`createProject`, `openProject`, `renameProject`, `updateOptions` by a `Patch`, a deep partial that reaches a nested object's field alone, `applyPatch` in `core/data.ts`, ignored for another layout than the open project's, `resetOptions`, which keeps the id and name, `deleteProject`, which opens the deleted open project's neighbor in `projectList`, and `importProject`, which adds a project or replaces the one with its id), each changed project passing through its layout's `normalize`, so what a command means is decided there, not in the UI; ids, and the `Environment` `createProject` and `resetOptions` take the defaults in, come in the commands, made by `ui/useWorkspace`, so the reducer stays pure. `useWorkspace` holds the workspace and saves it after each change through `storage.ts`, its repository: `loadWorkspace`, and `saveWorkspace(previous, next)`, which writes only what changed. Storage keeps one key per project, so two tabs editing different projects don't overwrite each other: `calendarium-project:<id>` (one serialized project, compact; the key's id is authoritative, and records it can't read are skipped and left as they are), `calendarium-project-backup:<id>` (a record a later version wrote, kept before this one overwrites it) and `calendarium-workspace` (`{ version, app, open }`, also the marker that the 5.x data was migrated); the prefixes matter, the GitHub Pages origin being shared with the user's other project pages. The 5.x data (`calendarium-config`) is migrated on the first load without a workspace record, the one load that writes (the projects first and the record last, so the ids stay put and StrictMode's second load just loads them): an unnamed project of each layout whose options differ from its defaults, the year aside, and always of the layout that was shown, which opens; `calendarium-config` is left as it is, for a rollback to 5.x. A file and a stored project are the same JSON, the serialized project (`projectDocument.ts`, its only reader and writer: `PROJECT_FORMAT`, `serializeProject(project, { pretty })`, `parseProjectDocument`): `{ format, version, app, id, name, layout, options }`, the tags beside the options so no option can collide with one, the options' groups in sidebar order (the key order of each layout's `defaults()`), every value written, defaults included, so a change of default never changes how an old calendar prints. Reading one, another format, or `PROJECT_FORMAT` before 6, is not a project (`notProject`), and an unknown layout is rejected with its own reason (`unknownLayout`, a later version's); a missing or invalid id reads as `null`, a name that isn't a string as `''`, and the options are read field by field by `parseOptions`, `ignored` listing the invalid ones by path (`content.schedule.firstHour`). `projectFile.ts` keeps what is particular to files: the file name (`projectFile`: the project's name in lowercase, whitespace and `\/:*?"<>|` as `-`, or `calendar-<layout>-<year>.json` when it has none) and reading a file (`readProjectFile(file)`, refusing one over `MAX_PROJECT_FILE_SIZE`, 1 MB, unread, then `parseProjectFile(text, fileName)`, an `OpenedProjectFile`), a legacy file's project being named after the file, unless the app generated that name.
- `src/preferences/` — the viewer's own settings, apart from any calendar: never printed, never in a project file. `Preferences` (`Preferences.ts`, with `defaultPreferences`, `PREFERENCE_VALIDATORS` and `parsePreferences`, read field by field like a layout's options) holds the sidebar width, the open sidebar section (`withSectionToggled`: one open at a time) and the preview's zoom (`previewZoom`: a whole percent from `MIN_ZOOM` to `MAX_ZOOM`, the menu's `ZOOM_LEVELS` or in between, or one of the fits `ZOOM_FITS`; `zoomScale` resolving a fit from the preview's size, `zoomedIn` / `zoomedOut` stepping between levels, `zoomAt` rounding a scale, in `zoom.ts`); `storage.ts` loads and saves it under one key, keeping the fields a later version stored, and reads the separate keys of builds before 4.6.0 until it first saves. `ui/usePreferences` holds it; `App` passes the width to the `Sidebar`, which keeps it within the window, the open section to the `WorkspaceForm`, which gives its `Section`s an `OpenSections` context, and the zoom to the `Preview`, which draws its `ZoomBar` over the pages and keeps the middle of the view in place when zooming (with the wheel, the point under the pointer); `useZoomGestures` zooms it with Ctrl (or ⌘) and +, − or 0 while the focus is in the preview, and with Ctrl (or ⌘) and the wheel, as a trackpad's pinch sends, over it, in place of the browser's zoom. The `Preview` also draws the `PageIndicator`: the page showing the most of itself in the view (`useCurrentPage`), in reading order, with a booklet's sheet side, and the page before, after or typed in. A new preference is a field, its default and its validator there, and a control in the UI.
- `src/ui/` — `sidebar/` holds the `WorkspaceForm`: the `ProjectSection` (New project…, Change project… (the `OpenProjectDialog`, the projects one per row, scrolling past about eight, a radio group with its radios hidden, the open one chosen, Open or a double click opening another) and Delete project, then, past a separator, the file actions Open a project file and Save project to a file, then, past another, Print (disabled without a project), above the open project's name and its layout, shown read only; opening a file of a project already kept, or deleting one, asks first), then the open project's form, keyed by its id so half-typed drafts don't carry over, which combines the sections (the shared `CalendarSection`, `EventsSection`, `MiniMonthSection`, `FooterSection`, `PageSection` in `sidebar/`, and sections only one layout uses, like `HeaderSection` or `YearContentSection`, in that layout's `ui/` folder; each typed `OptionsSectionProps<C>` for the options it edits, or for the one group it edits (`CalendarSection` on `CalendarOptions`, `PageSection` on `PageSetup`, `FooterSection` on `PageFooter`), the form then giving it `optionsGroup(props, key)`, whose update patches the group inside the options; with their `defaults`, which its `Section`'s `onReset` button restores once confirmed on the veil it lays over the fields, passing its group's defaults whole (`onUpdate(defaults)`), and a nested group inside it patched by a named handler (`{ schedule: patch }`); `MonthGridFields`, `MiniMonthFields` and `ScheduleFields` take `OptionsFieldsProps<C>`, without defaults) built on the typed controls in `fields/` (`SelectField`, `NumberField`, …); `preview/Preview` renders the open project's layout with its options, and `preview/EmptyPreview` a New project button when no project is open. `App` holds whether the `NewProjectDialog` (a name, optional, and the layout) shows: the project section and the empty preview both open it, and it opens by itself on a first launch and once the last project is deleted. Dialogs are `ui/components/Dialog`: a native `<dialog>` opened with `showModal` while it is mounted, whose primary action submits its form, Escape and its close button cancelling, the focus going to its checked radio, or its first field, or to Cancel, and back once it closes, or to its `returnFocus` when there is nothing to go back to (a project created on a first launch or from the empty preview focuses Change project…) (`src/test/setupDom.ts` gives jsdom `showModal` and `close`); `window.confirm` is not used. Each layout's UI is one folder inside the layout's, `layouts/<layout-id>/ui/`, whose `index.ts` exports a `LayoutView` (`Component`, `Form`, short `name` and picker `label`); `ui/layouts/registry.ts` collects them in `LAYOUT_VIEWS` and exposes `layoutView(id)`. Parts several layouts draw (`Page`, `CalendarHeader`, `MiniMonth`, `usePagePlan`) stay in `ui/layouts/`, with `LayoutView` and the registry. Everything one layout has, its domain and its UI, is in its one folder, `layouts/<layout-id>/`.

### Layouts

Four layouts, `yearly`, `monthly`, `weekly` and `daily`. Each one's folder has a `README.md` describing what it prints, its options and the rules they follow, its migration steps, its files and its own domain terms: read it before changing that layout, and update it with the layout. Each is planned by a pure function in `layouts/<layout-id>/pages.ts`, `(options, model) => plan`, that says what every sheet holds, and drawn by its component in `layouts/<layout-id>/ui/`, which gets the plan from `usePagePlan(plan, options)` and only turns it into markup. What several layouts share stays here. The heading alignments are in `layouts/heading.ts`: `HEADING_ALIGNS` (left, center, right) for the month's `header.alignment`, nothing being beside its heading, and `HEADING_ALIGNMENTS`, adding `auto`, for the week's `header.alignment`; their sidebar options share labels in `ui/sidebar/fieldOptions.ts`. Every layout's heading font size (pt; each layout's `header.fontSize`) is checked there too (`isHeadingFontSize`) and edited by `ui/sidebar/HeadingFontSizeField`. The schedule options (`HourSchedule`: `hourFormat`, `firstHour`, `lastHour`) are shared by the week and day layouts through `layouts/schedule.ts` (defaults, validators, the `orderHours` normalize) and `ui/sidebar/ScheduleFields` (the week and day layouts' `content.schedule`, `orderContentHours` ordering it); the footer options (`footer`, a `PageFooter`: `show`, `height`) likewise through `layouts/footer.ts` and `ui/sidebar/FooterSection`, a section of its own; the month grid options (`MonthGridOptions`: `weekdayFormat`, `highlightWeekends`, `showWeekNumbers`) likewise through `layouts/monthGrid.ts` and `ui/sidebar/MonthGridFields`, shown in `YearContentSection` for the year layout's 12 months (its `content` group, which adds `monthSize`) and in the month layout's `MonthContentSection` (its `content` group, which adds the cells' settings and the `dayNumber` group; a grid has room for abbreviated weekday names only, `MONTH_GRID_WEEKDAY_FORMATS`, except the month page's, whose validator and `weekdayFormats` allow `full`); a mini month's look is `MiniMonthStyle` (the grid options plus `showYear`, whether its title names the year, and `size`, one of `MINI_MONTH_SIZES`), edited by `MiniMonthFields`; the day layout's `miniMonth` is a `MiniMonthOptions` (the style plus `show` and `showEvents`), edited by the shared `MiniMonthSection`, and the month and week layouts' `miniMonth` (the style plus `showPreviousMonth` and `showNextMonth`, or `showCurrentMonth`, `showNextMonth` and `showEvents`) each by its own `MiniMonthsSection`. Each size is defined once, in `ui/layouts/MiniMonth.module.css`: one class per size setting the box (`--mini-month-width`, `--mini-month-height`) and the text; `miniMonthSizeClass` gives it, and a layout puts it on the header holding the mini month, whose corner it sizes by those variables.

A layout takes its own options as `options` (`LayoutOptions[id]`) and renders its own `Page`s (`ui/layouts/Page.tsx`, one paper sheet each, given `setup={options.page}`), so it decides the page count; consecutive pages print on separate sheets. A rule deciding what a sheet shows goes in the plan, not the component: `normalize` holds the rules on stored values, the plan the rules on derived ones (the resolved week start, the year's weeks, the content box). A plan starts from the `CalendarModel` (`calendarModel(options)` in `layouts/common.ts`: resolved week start, the year's months and month names), builds shared label arrays (weekday names, hour labels) once so the memoized pages (`WeekPage`, `DayPage`) keep equal props, and describes the drawn elements by their component's props, spread into it, like `MiniMonthPlan` (`layouts/monthGrid.ts`) into the shared `MiniMonth`. Reuse `CalendarHeader` for the page heading (`size="large"` or `"compact"`). Weekend highlighting rules live in `core/weekend.ts`.

Adding a layout: a `layouts/<layout-id>/` folder with a `README.md` (as the other layouts' are) and an `index.ts` (its entry point) that exports `defineLayout('<layout-id>', spec)`, listed in `LAYOUTS` (`layouts/index.ts`); a `layouts/<layout-id>/options.ts` with its options type and `LayoutSpec` (`normalize: normalizeCommon`, the shared options' rules, when it has no cross-field rules of its own), with an `options.test.ts`, and a `pages.ts` with its plan and a `pages.test.ts`; a `layouts/<layout-id>/ui/` folder with its component (drawing the plan), form and `LayoutView`, listed in `LAYOUT_VIEWS` (compile-enforced, as the spec's fields are; `layers.test.ts` checks the folder is named after the id).

### Config options

Every option belongs to one layout's set, and every option is in a group: one per drawn element, which is one per sidebar section, so a section edits one group and resets it whole. `CommonOptions` holds only what every layout uses with the same meaning: the `calendar` group (`CalendarOptions`: `year`, `locale`, `weekStart`), the `events` (a list of lines, at most `MAX_EVENT_LINES` when read) and `page`. Each layout has its own `header`, `miniMonth` and `content` types (`YearlyHeader`, `WeeklyContent`, …, in `layouts/<layout-id>/options.ts`, in sidebar order: calendar, events, header, miniMonth, content, footer, page), built from the groups several layouts share, each defined once with its type, defaults, validators and fields component: `PageFooter` (`footer`), `HourSchedule` (`content.schedule`), `MonthGridOptions`, `MiniMonthStyle` and `MiniMonthOptions`. A prefix naming a sub-element of two or more fields becomes a nested group (`content.schedule`, `content.dayNumber`, `content.genkoYoshi`); a single field keeps its descriptive name (`content.ruledLineSpacing`). A field name means the same thing in every layout that has it, which is up to naming (`fontSize` is always pt), though its type may differ (`header.alignment` has `auto` on the week layout only), so a field that would mean something else gets another name. Adding an option touches: `CommonOptions` (every layout, `layouts/common.ts`), a shared group, or one of a layout's groups in `layouts/<layout-id>/options.ts`, its default in `commonDefaults()`, the group's defaults or that layout's spec `defaults`, a validator in `COMMON_VALIDATORS` (`layouts/common.ts`), the group's validators or that layout's spec `validators` (a nested `Validators` table per group), and a control in the matching section (`ui/sidebar/*Section.tsx` for shared options, the layout's `ui/` folder for its own), shown by that layout's form. The compiler enforces the default and the validator. A rule that ties several fields together (e.g. `firstHour` ≤ `lastHour`, `orderContentHours`) goes in that layout's spec `normalize` (or, for the shared options, in `normalizeCommon`, which every layout's `normalize` starts from, like `normalizePage`: margins that differ, or mirrored margins, turn equal margins off), which runs after parsing and after every reducer change, so layouts render the options as is and form limits are only a hint. For a choice between fixed values, declare a `const` array next to the concept it belongs to (`core/` for a generic one, the layout's folder when only it uses the set) and derive the type from it (`(typeof X)[number]`); the validator is `oneOf(X)` and the select options are `optionsFrom(X, labels)`, which fails to compile if a value has no label.

The app version in `package.json` (semver) is the only version to edit; `workspace/version.ts` exposes it as `APP_VERSION` (shown in the sidebar) and its major part as `FORMAT_VERSION`, the version of the data format. Stored projects and files are one shape, the serialized project (`{ format, version, app, id, name, layout, options }`, `format` being `PROJECT_FORMAT`), tagged with both, as is the workspace record (`{ version, app, open }`). Data without a valid `version` (from `FIRST_FORMAT_VERSION` = 3 up) is ignored, and a file without a known `format` is rejected. A release bumps `package.json`: a minor or patch for anything older builds still read correctly (adding a field needs no major), a major for a change that would misread older data (renamed or restructured field or value). A major release appends one step to `PROJECT_MIGRATIONS` in `workspace/migrations.ts`, which storage and files share, and describes the new shape in its doc comment; a test fails until `FIRST_PROJECT_VERSION` (6) plus its length reaches the new major (the workspace record needs a step list only once its shape changes). The formats of 3 to 5 are frozen in `workspace/legacy.ts`: their steps (`LEGACY_STORAGE_MIGRATIONS`, `LEGACY_FILE_MIGRATIONS`), the old layout ids (`LEGACY_LAYOUT_IDS`) and the conversions to 6, `legacyFile` (files tagged `LEGACY_FILE_FORMAT`, versions 3 to 5 only) and `legacyWorkspace`, which map the id first, then apply each layout's step from 5. A layout's options changing is a step in that layout's `migrations`, keyed by the version it starts from: steps keyed 3 to 5 run through both legacy paths, steps from 6 through `PROJECT_MIGRATIONS` (`layoutInProject(version)`; a step that also changes the shape does that around it; the helpers in `layouts/migrations.ts`, `groupFields`, `commonGroups`, `footerGroup` and `scheduleGroup`, move flat fields into their groups); a test fails if a layout's step is not applied. A release is a published GitHub release tagged `vX.Y.Z` matching `package.json` (only that deploys, `deploy-pages.yml`, which also attaches the built site to the release as `calendarium-X.Y.Z.zip`), so before bumping compare `package.json` with the latest tag on the remote (`git fetch --tags`, then `git describe --tags --abbrev=0`): equal means that version is released and a change needs a new bump; higher means a bump is pending, and a change only raises it if it needs a larger part (a breaking change on a pending minor or patch makes it the next major), while a further breaking change on a pending major amends that major's migration steps instead of appending new ones. Note every user-facing change under `## Unreleased` in `CHANGELOG.md` (Added, Changed, Fixed; a major also says what older settings and files become), and on a release rename that section to the version and its date, starting a new empty `## Unreleased` above it. Data from a later version (a later major, or a later `app` of the same major) is read best-effort: a project is written only once it changes (`saveWorkspace` writes only what changed, and loading writes nothing but the one 5.x migration), a later version's record is backed up under `calendarium-project-backup:<id>` before being overwritten, and an opened file shows a notice. A nested object like `page` is checked by a nested `Validators` table (`FieldCheck`), field by field, so one bad field keeps the others.

### Printing

- Paper sizes are defined once in `src/core/paper.ts` (`PAPERS`: CSS name and mm dimensions). `Page` sizes its box in mm from it (`contentBox` gives the area inside the margins, for layouts that size content from the page), so the screen preview matches print, and `Preview` renders a `<style>` with the matching `@page { size }` rule. A new paper size is one entry there plus its label in `PageSection`.
- The preview's zoom scales the pages with the CSS `zoom` property on screen only (`Preview.module.css`), so printing always keeps the paper size.
- `Page` clips content to the paper, so on screen it shows a badge when its content doesn't fit inside the margins (`useOverflow`, checked only while the page is visible, so it doesn't undo `content-visibility`), and reports it through `PageOverflowContext` (`ui/layouts/pageOverflow.ts`) to the `Preview`, which counts the pages that don't fit (`useOverflowCount`) in one `role="status"`, announced, rather than a live region per page. `index.css` turns transitions and animations off under `prefers-reduced-motion: reduce`. `Preview` wraps the layout in `PreviewErrorBoundary`, which offers to reset the project's settings, keeping its id and name, instead of a blank screen. Any other error is caught by `ui/components/AppErrorBoundary`, around `App` in `main.tsx`, which offers to reload and to save each stored project to a file.
- A booklet (`PageSetup.booklet`) keeps the paper size and orientation as each page's and prints two pages on each side of a sheet twice that size (`sheetDimensions`, the `@page` size then given in mm): `ui/preview/Booklet` wraps the layout in a grid and, from the pages actually drawn, appends blank pages to a multiple of 4 and places each on its sheet side by `bookletSides` (`core/booklet.ts`), leaving the pages in reading order in the document so mirrored margins still count them. A booklet's spine is its fold (`normalizePage`). Layouts draw the same pages either way. Outside a booklet, a layout whose `LayoutView.facingPages` says its pages face each other (the week and day layouts with two pages per week or day) is shown, on screen only, as spreads by `ui/preview/Spreads`: the first page alone on the far side of the spine, then each even page facing the next odd one, side by side for a `left` spine, one above the other for a `top` one, a ring binding drawn between them (not printed) so they read as separate sheets, unlike a booklet's; the zoom's fits then fit a spread (`spreadDimensions`, in `ui/preview/spreadLayout.ts`).
- Printing targets Chrome/Chromium: Save as PDF, paper size matching the selection (twice it for a booklet, printed double-sided flipping on the short edge), Margins: None, Scale: 100%.

## Code style

- Indent with tabs (enforced by Prettier and `.editorconfig`); Markdown and YAML use 2 spaces.
- Both tsconfigs set `"strict": true` explicitly; `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` were tried and stay off, for the reasons in `doc/typescript-strictness.md`.
- Run `npm run format` after editing. It also sorts imports (`@ianvs/prettier-plugin-sort-imports`, configured in `.prettierrc.json`): Node built-ins, then packages, a blank line, then relative paths, each block alphabetical; side-effect imports (`import './index.css'`) stay where they are and split the blocks around them.
- oxlint (`.oxlintrc.json`) runs the `react`, `typescript`, `oxc`, `import`, `jsx-a11y` and `unicorn` plugins, correctness as errors and suspicious as warnings, and `npm run lint` must show neither. A finding that is deliberate gets an `// oxlint-disable-next-line <rule> -- <reason>` comment, not a config change; tests may use `!` and nested helpers.
- A `.tsx` file exports only components (oxlint `react/only-export-components`, for Fast Refresh); put shared constants in a `.ts` file next to it, as each layout folder's `index.ts` does.

### Styles

- Each component's styles live in a co-located CSS Module: `ProjectSection.tsx` → `ProjectSection.module.css`, imported as `import styles from './ProjectSection.module.css'`.
- Use camelCase class names (`.a4Portrait`) so they read as `styles.a4Portrait`.
- Keep a component's print overrides (`@media print`) in its own module file.
- `src/index.css` holds only global styles: reset, `:root` fonts, colors, spacing and rule widths (CSS variables), `body`, and the global `@page { margin: 0 }`. No component classes there.
- Size anything inside a printed page in `mm`/`pt`, never `px`.
- Draw thin lines as borders, never as background gradients: a sub-pixel gradient line can vanish depending on zoom and pixel position (Firefox especially), while a non-zero border always gets at least one device pixel.
- Use the color variables from `:root` in `index.css` (`var(--color-weekend)`), never literal colors in a module; add a variable when a new color is needed.
- Space the app's chrome with the `--space-*` scale in `index.css`; the sidebar's padding (`--sidebar-padding`, which the section bands and the form reach across) and the space between pages on screen (`--page-gap`) have their own tokens. Printed rules are `--rule-light` or `--rule-heavy`.

### Event handlers

- Never write event handlers inline in JSX (`onClick={() => ...}`). Extract them as named functions and pass them by reference: `onClick={handlePrintClick}`.
- Name them `handle<Element><Event>`, e.g. `handlePrintClick`, `handleYearChange`.
- If the handler does not use props or state, declare it at module level, outside the component. Otherwise declare it inside the component, before the `return`.
- Pass the function itself, not a call to it: `onClick={handleX}`, not `onClick={handleX()}`.
- Wrap a handler in `useCallback` only when it needs a stable identity (passed to a `React.memo` child or used in a hook dependency array).
- For handlers that need per-item arguments (e.g. list rows), use a `data-*` attribute read from `event.currentTarget`, or move the handler into a child component.
