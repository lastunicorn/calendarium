# Calendarium

Browser app (Vite + React + TypeScript) that generates a calendar to print on paper.

## Commands

- `npm run dev` / `npm run build` / `npm test` / `npm run test:e2e` (Playwright) / `npm run lint` (oxlint) / `npm run format` (`format:check` to verify only) / `npm run typecheck`
- Single test file: `npx vitest run src/core/calendar.test.ts`; single test by name: `npx vitest run -t "leap year"`
- Unit tests are plain `src/**/*.test.ts` files, DOM-free, covering `core/`, `layouts/`, `workspace/` and `preferences/`. A layout's own rules are tested in its folder (its options in `options.test.ts` through `parseOptions`, its migration steps in `migrations.test.ts`, what its pages hold in `pages.test.ts`), what every layout's spec must do in `layouts/index.test.ts` (run for each id in `LAYOUT_IDS`), and the host's tests in `workspace/` and `ui/` check only the mechanics, through any layout. Component tests are `src/**/*.test.tsx` (Vitest `component` project: jsdom + Testing Library, setup in `src/test/setupDom.ts`); they check structure only (page counts, which form sections show, the import flow), never appearance. What a layout draws and which sections its form shows are tested next to its component and form in `layouts/<layout-id>/ui/` (`formSectionTitles` in `src/test/formSections.ts` renders a form alone). Run one project with `npx vitest run --project unit` (or `component`).
- CI (`.github/workflows/build-master.yml`) runs `format:check`, `lint`, `typecheck`, `test`, `build` and `test:e2e`, in that order; run the same before considering a change done.
- `e2e/print.spec.ts` (Playwright, Chromium) builds the app, prints each layout to PDF and checks the page count and paper size, and that no page's content is clipped in print media. First run needs `npx playwright install chromium`.

## Architecture

Five folders, one per bounded context, from the bottom up: `core` ← `layouts` ← `workspace` ← `preferences` ← `ui`. Each imports only the folders below it, and only `ui/` uses React (a layout's UI, in `layouts/<layout-id>/ui/`, is `ui/`). Each layout is one unit, like a plugin of the host (everything outside the layouts' folders): its files import only its own files and the host's, never another layout's, and the host knows a layout only through its entry points, its domain `layouts/<layout-id>/index.ts` and its UI's `layouts/<layout-id>/ui/index.ts`, imported by the registries alone (`layouts/index.ts`, `ui/layouts/registry.ts`). `src/layers.test.ts` fails on any import that breaks these rules, and on a layout folder not named after an id in `LAYOUT_IDS`. It lists the files with `import.meta.glob`, so `vite.config.ts` keeps Vitest from caching such a module (`freshGlobs`), which would otherwise miss files added since.

- `src/core/` — the generic subdomains: calendar, languages and paper, knowing nothing of layouts or settings. `buildMonth` always returns 6 weeks so every month has the same height. A date is a `PlainDate` (`{ year, month, day, weekday, key }`, `key` = `YYYY-MM-DD`, the React key, `weekday` a `Weekday`, 0 = Sunday … 6 as in `Date.getDay()`; a `CalendarDay` extends it, as does a `WeekDay`, seven of which make a `Week`), never a `Date`: `plainDate` builds one, a weekday's column from the week start is `weekdayColumn`, and `utcDate` (UTC midnight, `setUTCFullYear`, so no DST and years below 100 as written) is the only place a `Date` is built, for `Intl` formatting (`dateFormatter` formats in UTC). `locale.ts` lists the supported `LOCALES` and derives month/weekday names from `Intl.DateTimeFormat` (through the cached `dateFormatter`) and the default week start from `Intl.Locale` week data. `events.ts` reads the event list (`CommonOptions.events`, kept as typed: one `YYYY-MM-DD Name` per line, year `0000` for every year) into `CalendarEvent`s (`parseEvents`) and names a date's events (`eventNames`); `calendarModel` parses it once, and the month, week and day plans give each day of their month or year its `events`, and the year plan gives each month the `eventDays` its `MiniMonth` circles. Any other text printed on a page comes from the layout's own messages table (`layouts/<layout-id>/messages.ts`, like `DAY_PAGE_MESSAGES`), never a literal in a component, so a calendar is printed in one language; the app's own UI stays English. Each layout keeps its own table, even for text another layout prints too (the week and day layouts both have `week`), so layouts stay independent of one another. A new locale is one entry in `LOCALES`, its messages in each layout's table and its label in `CalendarSection` (compile-enforced). The Gregorian range (`MIN_YEAR`, `isYear`) is in `calendar.ts`; the page setup (`PageSetup`, `Margins`, their `PAGE_VALIDATORS`) in `paper.ts`; the generic checks (`Validators`, `oneOf`, …) and `copyValid`, which applies a `Validators` table to untrusted data field by field, in `validation.ts`.
- `src/layouts/` — the core domain: what each layout is and prints. `index.ts` lists the layouts once, in `LAYOUTS` (the picker's order), each the `defineLayout(id, spec)` its folder's `index.ts` exports, and derives the rest from it: `LayoutId`, `LAYOUT_IDS`, each layout's options (`LayoutOptions`: `YearPerPageOptions`, `MonthPerPageOptions`, `WeekPerPageOptions`, `DayPerPageOptions`, each extending `CommonOptions` from `common.ts`, which `defineLayout` requires) and the specs. The id is stored in settings and files, so it never changes once released. Each layout's knowledge of its options is one `LayoutSpec` in `layouts/<layout-id>/options.ts`, next to its options type: `defaults`, `validators` (extending `COMMON_VALIDATORS`), `normalize` and `migrations` (its own steps between format versions, in `layouts/<layout-id>/migrations.ts`, `{}` when it has none); `parseOptions(spec, data)` (`LayoutSpec.ts`) reads untrusted options by them. `index.ts` collects the specs in `LAYOUT_SPECS` and exposes `layoutSpec(id)`, `defaultLayoutOptions`, `normalizeLayout`, `migrateLayoutOptions` and `mapLayouts`; the first of the `LAYOUT_IDS` is the layout shown by default. Everything only one layout uses lives in its folders; what several share stays in the host (`common.ts`, `monthGrid.ts`, `schedule.ts`, `heading.ts`, `migrations.ts`). Rules a layout's pages follow sit next to its options, like `week-per-page/cells.ts` (`weekCells`, `splitWeekCells`).
- `src/workspace/` — the saved settings, apart from the viewer preferences: the single `Workspace` (`Workspace.ts`, with `defaultWorkspace`), the active `layout` plus `layouts`, one remembered set of options per layout. Switching layouts copies nothing, so each layout gets back its own values. `Workspace` is the aggregate root: it changes only through the commands of the pure `workspaceReducer` (`selectLayout` / `update` one layout's fields / `newProject` / `openProject`), so what a command means is decided there, not in the UI; `ui/useWorkspace` holds it and persists it through `storage.ts` (its repository: `loadWorkspace`, `saveWorkspace`) on every change; `parseWorkspace` brings untrusted stored data to the current shape (`migrations.ts`) and reads each layout's options with `parseOptions`, field by field, falling back to that layout's defaults. Saving, opening and starting a new project act on one project, a layout with its options (`Project`; the shown one is `activeProject`, in `Workspace.ts`): a file holds one project, flat, tagged with `layout`; `projectFile.ts` builds it (`projectFile`, which also names it) and reads it (`parseProjectFile`), so the `LayoutSection` only downloads and reports.
- `src/preferences/` — the viewer's own settings, apart from any calendar: never printed, never in a project file. `Preferences` (`Preferences.ts`, with `defaultPreferences`, `PREFERENCE_VALIDATORS` and `parsePreferences`, read field by field like a layout's options) holds the sidebar width and the open sidebar section (`withSectionToggled`: one open at a time); `storage.ts` loads and saves it under one key, keeping the fields a later version stored, and reads the separate keys of builds before 4.6.0 until it first saves. `ui/usePreferences` holds it; `App` passes the width to the `Sidebar`, which keeps it within the window, and the open section to the `WorkspaceForm`, which gives its `Section`s an `OpenSections` context. A new preference is a field, its default and its validator there, and a control in the UI.
- `src/ui/` — `sidebar/` holds the `Toolbar` (print) and `WorkspaceForm`: the `LayoutSection` (the picker, above the saving, opening and starting over of the current project), then the active layout's form, which combines the sections (the shared `CalendarSection`, `EventsSection`, `MiniMonthSection`, `PageSection` in `sidebar/`, and sections only one layout uses, like `HeaderSection` or `YearContentSection`, in that layout's `ui/` folder; each typed `OptionsSectionProps<C>` for the options it edits, with their `defaults`, which its `Section`'s `onReset` button restores through `defaultFields` once confirmed on the veil it lays over the fields; `MonthGridFields` and `ScheduleFields` take `OptionsFieldsProps<C>`, without defaults) built on the typed controls in `fields/` (`SelectField`, `NumberField`, …); `preview/Preview` renders the layout chosen by `workspace.layout` with that layout's options. Each layout's UI is one folder inside the layout's, `layouts/<layout-id>/ui/`, whose `index.ts` exports a `LayoutView` (`Component`, `Form`, short `name` and picker `label`); `ui/layouts/registry.ts` collects them in `LAYOUT_VIEWS` and exposes `layoutView(id)`. Parts several layouts draw (`Page`, `CalendarHeader`, `MiniMonth`, `usePagePlan`) stay in `ui/layouts/`, with `LayoutView` and the registry. Everything one layout has, its domain and its UI, is in its one folder, `layouts/<layout-id>/`.

### Layouts

Four layouts, `year-per-page`, `month-per-page`, `week-per-page` and `day-per-page`. Each one's folder has a `README.md` describing what it prints, its options and the rules they follow, its migration steps, its files and its own domain terms: read it before changing that layout, and update it with the layout. Each is planned by a pure function in `layouts/<layout-id>/pages.ts`, `(options, model) => plan`, that says what every sheet holds, and drawn by its component in `layouts/<layout-id>/ui/`, which gets the plan from `usePagePlan(plan, options)` and only turns it into markup. What several layouts share stays here. The heading alignments are in `layouts/heading.ts`: `HEADING_ALIGNS` (left, center, right) for the month's `monthHeadingAlignment`, nothing being beside its heading, and `HEADING_ALIGNMENTS`, adding `auto`, for the week's `headingAlignment`; their sidebar options share labels in `ui/sidebar/fieldOptions.ts`. The week and day layouts' `headingFontSize` (pt) is checked there too (`isHeadingFontSize`) and edited by `ui/sidebar/HeadingFontSizeField`. The schedule options (`HourSchedule`: `hourFormat`, `firstHour`, `lastHour`) are shared by the week and day layouts through `layouts/schedule.ts` (defaults, validators, the `orderHours` normalize) and `ui/sidebar/ScheduleFields`; the footer options (`PageFooter`: `showFooter`, `footerHeight`) likewise through `layouts/footer.ts` and `ui/sidebar/FooterFields`; the month grid options (`MonthGridOptions`: `weekdayFormat`, `highlightWeekends`, `showWeekNumbers`) likewise through `layouts/monthGrid.ts` and `ui/sidebar/MonthGridFields`, shown in `YearContentSection` for the year layout's main grid and in the month layout's `MonthContentSection` (a grid has room for abbreviated weekday names only, `MONTH_GRID_WEEKDAY_FORMATS`, except the month page's, whose validator and `weekdayFormats` allow `full`); a secondary mini month is the nested `miniMonth: MiniMonthOptions` (the grid options plus `show`, `showYear`, whether its title names the year, and `size`, one of `MINI_MONTH_SIZES`), edited by `MiniMonthSection`, whose form merges the patch into the nested object. Each size is defined once, in `ui/layouts/MiniMonth.module.css`: one class per size setting the box (`--mini-month-width`, `--mini-month-height`) and the text; `miniMonthSizeClass` gives it, and a layout puts it on the header holding the mini month, whose corner it sizes by those variables.

A layout takes its own options as `options` (`LayoutOptions[id]`) and renders its own `Page`s (`ui/layouts/Page.tsx`, one paper sheet each, given `setup={options.page}`), so it decides the page count; consecutive pages print on separate sheets. A rule deciding what a sheet shows goes in the plan, not the component: `normalize` holds the rules on stored values, the plan the rules on derived ones (the resolved week start, the year's weeks, the content box). A plan starts from the `CalendarModel` (`calendarModel(options)` in `layouts/common.ts`: resolved week start, the year's months and month names), builds shared label arrays (weekday names, hour labels) once so the memoized pages (`WeekPage`, `DayPage`) keep equal props, and describes the drawn elements by their component's props, spread into it, like `MiniMonthPlan` (`layouts/monthGrid.ts`) into the shared `MiniMonth`. Reuse `CalendarHeader` for the page heading (`size="large"` or `"compact"`). Weekend highlighting rules live in `core/weekend.ts`.

Adding a layout: a `layouts/<layout-id>/` folder with a `README.md` (as the other layouts' are) and an `index.ts` (its entry point) that exports `defineLayout('<layout-id>', spec)`, listed in `LAYOUTS` (`layouts/index.ts`); a `layouts/<layout-id>/options.ts` with its options type and `LayoutSpec` (`normalize: normalizeCommon`, the shared options' rules, when it has no cross-field rules of its own), with an `options.test.ts`, and a `pages.ts` with its plan and a `pages.test.ts`; a `layouts/<layout-id>/ui/` folder with its component (drawing the plan), form and `LayoutView`, listed in `LAYOUT_VIEWS` (compile-enforced, as the spec's fields are; `layers.test.ts` checks the folder is named after the id).

### Config options

Every option belongs to one layout's set. `CommonOptions` holds only what every layout uses with the same meaning (`year`, `locale`, `weekStart`, `page`); options describing one drawn element form a group (`HourSchedule`, `MonthGridOptions`: type, defaults, validators and a fields component, defined once) that the layouts drawing it mix in. A field name means the same type and the same thing in every layout that has it: the type is compile-checked (`SameFieldTypesCheck` in `layouts/index.ts`, whose error names the field), the meaning is up to naming, so a field that would mean something else gets another name. Adding an option touches: `CommonOptions` (every layout, `layouts/common.ts`), a group, or one layout's type in `layouts/<layout-id>/options.ts`, its default in `commonDefaults()` or that layout's spec `defaults`, a validator in `COMMON_VALIDATORS` (`layouts/common.ts`) or that layout's spec `validators`, and a control in the matching section (`ui/sidebar/*Section.tsx` for shared options, the layout's `ui/` folder for its own), shown by that layout's form. The compiler enforces the default and the validator. A rule that ties several fields together (e.g. `firstHour` ≤ `lastHour`) goes in that layout's spec `normalize` (or, for the shared options, in `normalizeCommon`, which every layout's `normalize` starts from, like `normalizePage`: margins that differ, or mirrored margins, turn equal margins off), which runs after parsing and after every reducer change, so layouts render the options as is and form limits are only a hint. For a choice between fixed values, declare a `const` array next to the concept it belongs to (`core/` for a generic one, the layout's folder when only it uses the set) and derive the type from it (`(typeof X)[number]`); the validator is `oneOf(X)` and the select options are `optionsFrom(X, labels)`, which fails to compile if a value has no label.

The app version in `package.json` (semver) is the only version to edit; `workspace/version.ts` exposes it as `APP_VERSION` (shown in the sidebar) and its major part as `FORMAT_VERSION`, the version of the data format. Stored data (`{ version, app, layout, layouts }`) and files (`{ format, version, app, layout, ...options }`, one layout, flat, `format` being `FILE_FORMAT`) are tagged with both. Data without a valid `version` (from `FIRST_FORMAT_VERSION` = 3 up) is ignored, and a file without the `format` is rejected. A release bumps `package.json`: a minor or patch for anything older builds still read correctly (adding a field needs no major), a major for a change that would misread older data (renamed or restructured field or value). A major release appends one step to `STORAGE_MIGRATIONS` and one to `FILE_MIGRATIONS` in `workspace/migrations.ts` and describes the new shape in their doc comments; a test fails until both lists reach the new major. A layout's options changing is a step in that layout's `migrations`, keyed by the version it starts from, which the host's steps apply (`layoutsInStorage(version)`, `layoutInFile(version)`; a step that also changes the format's shape does that around them); a test fails if a layout's step is not applied in both. A release is a published GitHub release tagged `vX.Y.Z` matching `package.json` (only that deploys, `deploy-pages.yml`, which also attaches the built site to the release as `calendarium-X.Y.Z.zip`), so before bumping compare `package.json` with the latest tag on the remote (`git fetch --tags`, then `git describe --tags --abbrev=0`): equal means that version is released and a change needs a new bump; higher means a bump is pending, and a change only raises it if it needs a larger part (a breaking change on a pending minor or patch makes it the next major), while a further breaking change on a pending major amends that major's migration steps instead of appending new ones. Note every user-facing change under `## Unreleased` in `CHANGELOG.md` (Added, Changed, Fixed; a major also says what older settings and files become), and on a release rename that section to the version and its date, starting a new empty `## Unreleased` above it. Data from a later version (a later major, or a later `app` of the same major) is read best-effort: storage is never written on load (`useWorkspace` saves only after a change), `saveWorkspace` backs such data up under another key before overwriting it, and an imported file shows a notice. A nested object like `page` is checked by a nested `Validators` table (`FieldCheck`), field by field, so one bad field keeps the others.

### Printing

- Paper sizes are defined once in `src/core/paper.ts` (`PAPERS`: CSS name and mm dimensions). `Page` sizes its box in mm from it (`contentBox` gives the area inside the margins, for layouts that size content from the page), so the screen preview matches print, and `Preview` renders a `<style>` with the matching `@page { size }` rule. A new paper size is one entry there plus its label in `PageSection`.
- `Page` clips content to the paper, so on screen it shows a badge when its content doesn't fit inside the margins (`useOverflow`, checked only while the page is visible, so it doesn't undo `content-visibility`). `Preview` wraps the layout in `PreviewErrorBoundary`, which offers a reset of the layout's settings instead of a blank screen.
- A booklet (`PageSetup.booklet`) keeps the paper size and orientation as each page's and prints two pages on each side of a sheet twice that size (`sheetDimensions`, the `@page` size then given in mm): `ui/preview/Booklet` wraps the layout in a grid and, from the pages actually drawn, appends blank pages to a multiple of 4 and places each on its sheet side by `bookletSides` (`core/booklet.ts`), leaving the pages in reading order in the document so mirrored margins still count them. A booklet's spine is its fold (`normalizePage`). Layouts draw the same pages either way.
- Printing targets Chrome/Chromium: Save as PDF, paper size matching the selection (twice it for a booklet, printed double-sided flipping on the short edge), Margins: None, Scale: 100%.

## Code style

- Indent with tabs (enforced by Prettier and `.editorconfig`); Markdown and YAML use 2 spaces.
- Run `npm run format` after editing.
- A `.tsx` file exports only components (oxlint `react/only-export-components`, for Fast Refresh); put shared constants in a `.ts` file next to it, as each layout folder's `index.ts` does.

### Styles

- Each component's styles live in a co-located CSS Module: `Toolbar.tsx` → `Toolbar.module.css`, imported as `import styles from './Toolbar.module.css'`.
- Use camelCase class names (`.a4Portrait`) so they read as `styles.a4Portrait`.
- Keep a component's print overrides (`@media print`) in its own module file.
- `src/index.css` holds only global styles: reset, `:root` fonts/colors (CSS variables), `body`, and the global `@page { margin: 0 }`. No component classes there.
- Size anything inside a printed page in `mm`/`pt`, never `px`.
- Draw thin lines as borders, never as background gradients: a sub-pixel gradient line can vanish depending on zoom and pixel position (Firefox especially), while a non-zero border always gets at least one device pixel.
- Use the color variables from `:root` in `index.css` (`var(--color-weekend)`), never literal colors in a module; add a variable when a new color is needed.

### Event handlers

- Never write event handlers inline in JSX (`onClick={() => ...}`). Extract them as named functions and pass them by reference: `onClick={handlePrintClick}`.
- Name them `handle<Element><Event>`, e.g. `handlePrintClick`, `handleYearChange`.
- If the handler does not use props or state, declare it at module level, outside the component. Otherwise declare it inside the component, before the `return`.
- Pass the function itself, not a call to it: `onClick={handleX}`, not `onClick={handleX()}`.
- Wrap a handler in `useCallback` only when it needs a stable identity (passed to a `React.memo` child or used in a hook dependency array).
- For handlers that need per-item arguments (e.g. list rows), use a `data-*` attribute read from `event.currentTarget`, or move the handler into a child component.
