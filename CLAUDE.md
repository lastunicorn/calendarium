# Printable Calendar

Browser app (Vite + React + TypeScript) that generates a calendar to print on paper.

## Commands

- `npm run dev` / `npm run build` / `npm test` / `npm run test:e2e` (Playwright) / `npm run lint` (oxlint) / `npm run format` (`format:check` to verify only) / `npm run typecheck`
- Single test file: `npx vitest run src/core/calendar.test.ts`; single test by name: `npx vitest run -t "leap year"`
- Unit tests are plain `src/**/*.test.ts` files, DOM-free, covering `core/`, `layouts/` (including what each layout's pages hold, in its `pages.test.ts`) and `config/`. Component tests are `src/**/*.test.tsx` (Vitest `component` project: jsdom + Testing Library, setup in `src/test/setupDom.ts`); they check structure only (page counts, which form sections show, the import flow), never appearance. Run one project with `npx vitest run --project unit` (or `component`).
- CI (`.github/workflows/build-master.yml`) runs `format:check`, `lint`, `typecheck`, `test`, `build` and `test:e2e`, in that order; run the same before considering a change done.
- `e2e/print.spec.ts` (Playwright, Chromium) builds the app, prints each layout to PDF and checks the page count and paper size, and that no page's content is clipped in print media. First run needs `npx playwright install chromium`.

## Architecture

Four folders, one per bounded context, from the bottom up: `core` ← `layouts` ← `config` ← `ui`. Each imports only the folders below it, and only `ui/` uses React; `src/layers.test.ts` fails on any import that breaks this.

- `src/core/` — the generic subdomains: calendar, languages and paper, knowing nothing of layouts or settings. `buildMonth` always returns 6 weeks so every month has the same height. A date is a `PlainDate` (`{ year, month, day, weekday, key }`, `key` = `YYYY-MM-DD`, the React key, `weekday` a `Weekday`, 0 = Sunday … 6 as in `Date.getDay()`; a `CalendarDay` extends it, as does a `WeekDay`, seven of which make a `Week`), never a `Date`: `plainDate` builds one, a weekday's column from the week start is `weekdayColumn`, and `utcDate` (UTC midnight, `setUTCFullYear`, so no DST and years below 100 as written) is the only place a `Date` is built, for `Intl` formatting (`dateFormatter` formats in UTC). `locale.ts` lists the supported `LOCALES` and derives month/weekday names from `Intl.DateTimeFormat` (through the cached `dateFormatter`) and the default week start from `Intl.Locale` week data. Any other text printed on a page comes from `PRINT_MESSAGES` (`messages.ts`), never a literal in a component, so a calendar is printed in one language; the app's own UI stays English. A new locale is one entry in `LOCALES`, its messages and its label in `CalendarSection` (compile-enforced). The Gregorian range (`MIN_YEAR`, `isYear`) is in `calendar.ts`; the page setup (`PageSetup`, `Margins`, their `PAGE_VALIDATORS`) in `paper.ts`; the generic checks (`Validators`, `oneOf`, …) in `validation.ts`.
- `src/layouts/` — the core domain: what each layout is and prints. `index.ts` lists the `LAYOUT_IDS` and each layout's options (`LayoutConfigs`: `YearPerPageConfig`, `MonthPerPageConfig`, `WeekPerPageConfig`, `DayPerPageConfig`, each extending `CommonConfig` from `common.ts`). Each layout's knowledge of its options is one `LayoutSpec` in `layouts/<layout-id>/options.ts`, next to its options type: `defaults`, `validators` (extending `COMMON_VALIDATORS`) and `normalize`; `index.ts` collects them in `LAYOUT_SPECS` and exposes `layoutSpec(id)`, `defaultLayoutConfig`, `normalizeLayout` and `mapLayouts`. Rules a layout's pages follow sit next to its options, like `week-per-page/cells.ts` (`weekCells`, `splitWeekCells`, `stacksDays`).
- `src/config/` — the saved settings: the single `AppConfig` (`AppConfig.ts`, with `defaultAppConfig`), the active `layout` plus `layouts`, one remembered set of options per layout. Switching layouts copies nothing, so each layout gets back its own values. `AppConfig` is the aggregate root: it changes only through the commands of the pure `configReducer` (`selectLayout` / `update` one layout's fields / `resetLayout` / `importLayout`), so what a command means is decided there, not in the UI; `ui/useCalendarConfig` holds it and persists it through `storage.ts` (its repository: `loadConfig`, `saveConfig`) on every change; `parseConfig` validates untrusted stored data field by field and falls back to each layout's defaults. Export, import and reset act on one layout: a file holds one layout's options, flat, tagged with `layout`; `configFile.ts` builds it (`exportLayoutFile`, which also names it) and reads it (`parseConfigFile`), so the `Toolbar` only downloads and reports.
- `src/ui/` — `sidebar/` holds the `Toolbar` (print, and export/import/reset of the current layout) and `ConfigForm`: the `LayoutSection` picker, then the active layout's form, which combines the sections (the shared `CalendarSection`, `AppearanceSection`, `MiniMonthSection`, `PageSection` in `sidebar/`, and sections only one layout uses, like `HeaderSection` or `DayPageSection`, in that layout's folder; each typed `ConfigSectionProps<C>` for the options it edits) built on the typed controls in `fields/` (`SelectField`, `NumberField`, …); `preview/Preview` renders the layout chosen by `config.layout` with that layout's options. Each layout's UI is one folder, `ui/layouts/<layout-id>/`, whose `index.ts` exports a `LayoutView` (`Component`, `Form`, short `name` and picker `label`); `ui/layouts/registry.ts` collects them in `LAYOUT_VIEWS` and exposes `layoutView(id)`. Parts several layouts draw (`Page`, `CalendarHeader`, `MiniMonth`, `usePagePlan`) stay directly in `ui/layouts/`. A layout's folder in `ui/layouts/` mirrors its folder in `layouts/`.

### Layouts

Four layouts. Each is planned by a pure function in `layouts/<layout-id>/pages.ts`, `(config, model) => plan`, that says what every sheet holds, and drawn by its component in `ui/layouts/<layout-id>/`, which gets the plan from `usePagePlan(plan, config)` and only turns it into markup. `year-per-page` (`planYearPage`: one page, the title or else the year above 12 `MiniMonth`s, every month 6 rows so they line up), `month-per-page` (`planMonthPages`: 12 pages, each headed by the month and year set per `monthHeadingAlignment` above a `MonthGrid` of large writing cells showing only the month's 4–6 rows via `visibleWeeks`, adjacent-month days in gray), `week-per-page` (`planWeekPages`: a `WeekPages` for each week from `weeksOfYear`, 53 or 54, headed by the `dateRangeName` of its days, set per `headingAlignment` (`headingAlign`: `auto` is left beside the mini month or over two pages, centered otherwise); its cells per `weekendDisplay` (`weekCells`: Saturday and Sunday may share a cell or be left out, and a week whose only days of the year are a hidden weekend gets no page), side by side or stacked per `weekDayDirection` (`stacksDays`: `auto` stacks them in portrait unless the week spans two pages); each day planned as a `WeekPageDay` with its weekday label, its month's name where the month changes and on each sheet's first day, its weekend highlight (`highlightWeekendDays`, never for a day of another year, `WeekDay.inYear`, drawn in gray) and whether it holds the hourly schedule (`weekPageLines` is `hours`, not in a cell two days share, nor for a day of another year); with `twoPagesPerWeek`, `splitWeekCells` puts the first three days on a first sheet whose header row shows the heading, and the rest on a second showing the mini month, each keeping the other part's space hidden; with `miniMonth.show`, a `MiniMonth` of the `weekMonth` beside the heading frames the week's row via `markedWeek`) and `day-per-page` (`planDayPages`: a `DayPages` for each day from `daysOfYear`, its heading the weekday or the date per `dayPageTitle` and the other one below, a details line ("Week N · Day N / 365", each part per its option), the heading in the weekend color per `highlightWeekendDays`, a corner `MiniMonth` marking the day via `markedDay`, and the `fills` of its one or two sheets, shared by every day: per `dayPageLines`, an hourly schedule from `firstHour` to `lastHour` labeled by `hourNames` in `hourFormat`, split in half over two sheets, or ruled lines filling the `contentBox`). The heading alignments are in `layouts/heading.ts`: `HEADING_ALIGNS` (left, center, right) for the month's `monthHeadingAlignment`, nothing being beside its heading, and `HEADING_ALIGNMENTS`, adding `auto`, for the week's `headingAlignment`; their sidebar options share labels in `ui/sidebar/fieldOptions.ts`. The schedule options (`HourSchedule`: `hourFormat`, `firstHour`, `lastHour`) are shared by the week and day layouts through `layouts/schedule.ts` (defaults, validators, the `orderHours` normalize) and `ui/sidebar/ScheduleFields`; the month grid options (`MonthGridOptions`: `weekdayFormat`, `highlightWeekends`, `showWeekNumbers`) likewise through `layouts/monthGrid.ts` and `ui/sidebar/MonthGridFields`, shown in `AppearanceSection` for the year and month layouts' main grids (a grid has room for abbreviated weekday names only, `MONTH_GRID_WEEKDAY_FORMATS`, except the month page's, whose validator and `weekdayFormats` allow `full`); a secondary mini month is the nested `miniMonth: MiniMonthOptions` (the grid options plus `show`), edited by `MiniMonthSection`, whose form merges the patch into the nested object.

A layout takes its own options as `config` (`LayoutConfigs[id]`) and renders its own `Page`s (`ui/layouts/Page.tsx`, one paper sheet each, given `setup={config.page}`), so it decides the page count; consecutive pages print on separate sheets. A rule deciding what a sheet shows goes in the plan, not the component: `normalize` holds the rules on stored values, the plan the rules on derived ones (the resolved week start, the year's weeks, the content box). A plan starts from the `CalendarModel` (`calendarModel(config)` in `layouts/common.ts`: resolved week start, the year's months and month names), builds shared label arrays (weekday names, hour labels) once so the memoized pages (`WeekPage`, `DayPage`) keep equal props, and describes the shared drawn elements by their component's props, spread into it: `MiniMonthPlan` (`layouts/monthGrid.ts`) into `MiniMonth`, `MonthGridPlan` into `MonthGrid`. Reuse `CalendarHeader` for the page heading (`size="large"` or `"compact"`). Weekend highlighting rules live in `core/weekend.ts`.

Adding a layout: an id in `LAYOUT_IDS` and an entry in `LayoutConfigs` (`layouts/index.ts`); a `layouts/<layout-id>/options.ts` with its options type and `LayoutSpec` (`normalize: unchanged` when it has no cross-field rules), listed in `LAYOUT_SPECS`, and a `pages.ts` with its plan and a `pages.test.ts`; a `ui/layouts/<layout-id>/` folder with its component (drawing the plan), form and `LayoutView`, listed in `LAYOUT_VIEWS` (all compile-enforced).

### Config options

Every option belongs to one layout's set. `CommonConfig` holds only what every layout uses with the same meaning (`year`, `locale`, `weekStart`, `page`); options describing one drawn element form a group (`HourSchedule`, `MonthGridOptions`: type, defaults, validators and a fields component, defined once) that the layouts drawing it mix in. A field name means the same type and the same thing in every layout that has it: the type is compile-checked (`SameFieldTypesCheck` in `layouts/index.ts`, whose error names the field), the meaning is up to naming, so a field that would mean something else gets another name. Adding an option touches: `CommonConfig` (every layout, `layouts/common.ts`), a group, or one layout's type in `layouts/<layout-id>/options.ts`, its default in `commonDefaults()` or that layout's spec `defaults`, a validator in `COMMON_VALIDATORS` (`layouts/common.ts`) or that layout's spec `validators`, and a control in the matching section (`ui/sidebar/*Section.tsx` for shared options, the layout's folder for its own), shown by that layout's form. The compiler enforces the default and the validator. A rule that ties several fields together (e.g. `firstHour` ≤ `lastHour`) goes in that layout's spec `normalize`, which runs after parsing and after every reducer change, so layouts render the config as is and form limits are only a hint. For a choice between fixed values, declare a `const` array next to the concept it belongs to (`core/` for a generic one, the layout's folder when only it uses the set) and derive the type from it (`(typeof X)[number]`); the validator is `oneOf(X)` and the select options are `optionsFrom(X, labels)`, which fails to compile if a value has no label.

The app version in `package.json` (semver) is the only version to edit; `config/version.ts` exposes it as `APP_VERSION` (shown in the sidebar) and its major part as `CONFIG_VERSION`, the version of the config format. Stored data (`{ version, app, layout, layouts }`) and files (`{ format, version, app, layout, ...options }`, one layout, flat, `format` being `FILE_FORMAT`) are tagged with both. Data without a valid `version` (from `FIRST_CONFIG_VERSION` = 3 up) is ignored, and a file without the `format` is rejected. A release bumps `package.json`: a minor or patch for anything older builds still read correctly (adding a field needs no major), a major for a change that would misread older data (renamed or restructured field or value). A major release appends one step to `STORAGE_MIGRATIONS` and one to `FILE_MIGRATIONS` in `config/migrations.ts` (one returning the data as is when that format did not change) and describes the new shape in their doc comments; a test fails until both lists reach the new major. A release is a published GitHub release tagged `vX.Y.Z` matching `package.json` (only that deploys, `deploy-pages.yml`), so before bumping compare `package.json` with the latest tag on the remote (`git fetch --tags`, then `git describe --tags --abbrev=0`): equal means that version is released and a change needs a new bump; higher means a bump is pending, and a change only raises it if it needs a larger part (a breaking change on a pending minor or patch makes it the next major), while a further breaking change on a pending major amends that major's migration steps instead of appending new ones. Note every user-facing change under `## Unreleased` in `CHANGELOG.md` (Added, Changed, Fixed; a major also says what older settings and files become), and on a release rename that section to the version and its date, starting a new empty `## Unreleased` above it. Data from a later version (a later major, or a later `app` of the same major) is read best-effort: storage is never written on load (`useCalendarConfig` saves only after a change), `saveConfig` backs such data up under another key before overwriting it, and an imported file shows a notice. A nested object like `page` is checked by a nested `Validators` table (`FieldCheck`), field by field, so one bad field keeps the others.

### Printing

- Paper sizes are defined once in `src/core/paper.ts` (`PAPERS`: CSS name and mm dimensions). `Page` sizes its box in mm from it (`contentBox` gives the area inside the margins, for layouts that size content from the page), so the screen preview matches print, and `Preview` renders a `<style>` with the matching `@page { size }` rule. A new paper size is one entry there plus its label in `PageSection`.
- `Page` clips content to the paper, so on screen it shows a badge when its content doesn't fit inside the margins (`useOverflow`, checked only while the page is visible, so it doesn't undo `content-visibility`). `Preview` wraps the layout in `PreviewErrorBoundary`, which offers a reset of the layout's settings instead of a blank screen.
- Printing targets Chrome/Chromium: Save as PDF, paper size matching the selection, Margins: None, Scale: 100%.

## Code style

- Indent with tabs (enforced by Prettier and `.editorconfig`); Markdown and YAML use 2 spaces.
- Run `npm run format` after editing.
- A `.tsx` file exports only components (oxlint `react/only-export-components`, for Fast Refresh); put shared constants in a `.ts` file next to it, as each layout folder's `index.ts` does.

### Styles

- Each component's styles live in a co-located CSS Module: `Toolbar.tsx` → `Toolbar.module.css`, imported as `import styles from './Toolbar.module.css'`.
- Use camelCase class names (`.a4Portrait`) so they read as `styles.a4Portrait`.
- Keep a component's print overrides (`@media print`) in its own module file.
- `src/index.css` holds only global styles: reset, `:root` fonts/colors (CSS variables), `body`, and the global `@page { margin: 0 }`. No component classes there.
- Size anything inside a printed page in `mm`/`pt`, never `px`.
- Draw thin lines as borders, never as background gradients: a sub-pixel gradient line can vanish depending on zoom and pixel position (Firefox especially), while a non-zero border always gets at least one device pixel.
- Use the color variables from `:root` in `index.css` (`var(--color-weekend)`), never literal colors in a module; add a variable when a new color is needed.

### Event handlers

- Never write event handlers inline in JSX (`onClick={() => ...}`). Extract them as named functions and pass them by reference: `onClick={handlePrintClick}`.
- Name them `handle<Element><Event>`, e.g. `handlePrintClick`, `handleYearChange`.
- If the handler does not use props or state, declare it at module level, outside the component. Otherwise declare it inside the component, before the `return`.
- Pass the function itself, not a call to it: `onClick={handleX}`, not `onClick={handleX()}`.
- Wrap a handler in `useCallback` only when it needs a stable identity (passed to a `React.memo` child or used in a hook dependency array).
- For handlers that need per-item arguments (e.g. list rows), use a `data-*` attribute read from `event.currentTarget`, or move the handler into a child component.
